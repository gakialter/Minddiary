# MindDiary v1.13.0 Security and Data Safety Audit

Status: evidence-driven audit of local files, attachments, backup/restore, API keys, updater, logs, and data boundaries.

Schema status: schema unchanged.

## Summary

Confirmed issues:

- No P1 security issue was confirmed from source/test evidence.
- Documentation drift can lead to unsafe operational assumptions about schema baseline and release state. This is tracked in the devex audit.

Potential issues:

- Subject ordering and non-task tie-breaker issues are data consistency, not security issues.
- ZIP restore replaces media directories before database restore, but it snapshots and rolls back on restore failure. This is a sensitive path that needs manual packaged validation before any release touching backup restore.

Non-issues supported by evidence:

- `local://` path traversal is actively guarded through realpath checks.
- ZIP restore rejects traversal and unexpected entries.
- AI API key is stripped from settings payloads and backup data.
- Release asset upload path is allowlist-backed and non-recursive.

## `local://` File Access

Classification: non-issue, evidence supported.

Evidence:

- `electron/main.ts` registers `protocol.handle('local', ...)` and resolves paths through `resolveLocalProtocolPath(request.url, app.getPath('userData'))`.
- `electron/pathSecurity.ts` decodes local URLs, rejects control characters, resolves the allowed base realpath, resolves target realpath, and checks `isPathInside`.
- `tests/pathSecurity.test.ts` covers traversal, encoded traversal, missing files, backslash traversal, case-insensitive Windows paths, symlink/junction outside, and allowed symlink/junction inside behavior.

Residual risk:

- Any future protocol handler that bypasses `resolveLocalProtocolPath` would reopen traversal risk.

## Attachments and Mistake Images

Classification: mostly non-issue, evidence supported.

Evidence:

- `electron/fileManager.ts` restricts uploaded attachment/image extensions and MIME types to image formats and caps image bytes at 10 MB.
- Saved filenames are generated from entry/mistake ids and timestamps, not raw user paths.
- `getAttachmentPath` and `getMistakeImagePath` resolve under managed directories and reject path traversal.
- Entry deletion deletes physical attachment files before SQL delete because SQL cascade does not remove disk files.
- Mistake image cleanup uses managed image reference keys to avoid deleting images still referenced elsewhere.

Residual risk:

- Filename collisions are timestamp-based. Probability is low, but rapid repeated image saves in the same millisecond could collide. This is not confirmed in tests.

Minimal future fix:

- Add random suffix or UUID to managed image filenames in a focused v1.13.x patch if collision evidence appears.

## Backup and ZIP Restore

Classification: non-issue for traversal, potential issue for operational sensitivity.

Evidence:

- `electron/backupRestore.ts` implements a stored-ZIP parser and rejects encrypted entries, data descriptors, non-UTF8 names, compressed entries, ZIP64, oversized entries, bad CRC, absolute paths, Windows drive paths, backslashes, null bytes, traversal segments, duplicate entries, and unexpected entry names.
- Allowed entries are `manifest.json`, `database.json`, and content under `attachments/` and `mistake_images/`.
- `validateManifest` rejects future schema versions and unsupported backup format versions.
- Media directories are backed up to a rollback root before replacement.
- If database restore fails after media replacement, restore attempts to roll back media snapshots.
- `normalizeBackupDatabaseData` strips sensitive settings and normalizes legacy backup shapes.

Risk:

- Restore is intentionally high impact: it deletes/replaces current media directories and database rows. Any future modification must preserve rollback semantics and `foreign_key_check`.

P2 risk template:

- Minimal fix: no current code fix; add a packaged manual restore smoke test to release checklist.
- Not fixing: release decisions may rely only on unit tests while filesystem permission or packaged path behavior differs.
- Fixing wrong: overly broad restore retries can corrupt media/database alignment.
- Recommended version: v1.13.1 docs/test checklist.
- Acceptance: restore from known schema 5 ZIP in packaged app keeps entries, attachments, mistake images, tasks, chapters, and AI key absence.
- Rollback: revert checklist/test-only changes; no schema rollback.

## API Key Storage

Classification: non-issue, evidence supported.

Evidence:

- `electron/settingsSecurity.ts` defines `SENSITIVE_SETTINGS_KEYS = ['aiApiKey']`.
- `buildSafeSettingsPayload` strips `aiApiKey` and returns only `aiApiKeyMasked` and `aiApiKeyPresent`.
- `electron/main.ts` settings API exposes patch-based `updateAI`; it rejects set-and-clear conflicts and empty API key strings.
- `electron/database.ts` refuses to persist a non-empty API key if `safeStorage.isEncryptionAvailable()` is false.
- `databaseBackupData.ts` strips sensitive settings from backup import/export normalization.

Residual risk:

- Existing legacy plaintext keys can be read once and migrated to encrypted storage when safeStorage is available. This is a controlled migration behavior, not a new leak.

## Auto Update and Release Assets

Classification: non-issue for allowlist controls; pending confirmation for actual signed release state.

Evidence:

- `package.json` config publishes to GitHub `gakialter/Minddiary`.
- `.github/workflows/release.yml` verifies tag/version/release-notes alignment.
- Release workflow runs Windows signing preflight and records whether artifacts are unsigned.
- `scripts/prepare-release-assets.mjs` defines exact asset names and rejects nested/unexpected/duplicate/empty assets.
- `scripts/verify-release-metadata.ts` validates updater metadata paths and packaged `app-update.yml` owner/repo.
- Release workflow uploads `release-upload/*` and `release-artifacts/*`, not recursive release directory globs.
- Tests verify internal binaries like `MindDiary.exe`, `elevate.exe`, and unpacked paths are rejected.

Pending confirmation:

- This audit did not verify current Windows signing certificate identity or SmartScreen reputation.

## Logs and Test Data

Classification: potential operational issue, not confirmed code bug.

Evidence:

- Local workspace includes logs and generated output directories; protected instructions say not to stage `release`, `dist`, `electron-dist`, logs, screenshots, or test databases.
- Release and CI workflows do not upload local logs by default.

Recommendation:

- Keep path-based staging only. Do not bulk add.

## Browser Fallback Sensitive Data

Classification: potential issue by design trade-off.

Evidence:

- Browser fallback stores data in localStorage through `DataContext` and `src/contexts/api/*`.
- AI key storage is managed by settings context/API; Electron settings strips/masks key. Browser fallback behavior should be checked before any browser-distribution claim.

Pending confirmation:

- This audit did not trace every browser fallback settings path for AI key persistence. Treat browser fallback as development/demo storage, not a secure secret store, unless a future audit proves otherwise.
