Status: audit complete with one new parity test file.

Schema status: schema unchanged.

Primary evidence:

- SQLite task behavior: `electron/repositories/studyTasksRepository.ts`.
- Browser fallback task behavior: `src/contexts/api/tasksApi.ts`.
- SQLite chapter behavior: `electron/repositories/subjectChaptersRepository.ts`.
- Browser fallback chapter behavior: `src/contexts/api/subjectChaptersApi.ts`.
- Fallback initialization/normalization: `src/contexts/DataContext.tsx`.
- New fixture parity tests: `tests/studyTaskParity.test.ts`.

## v1.13.0 Parity Claims

Verified facts:

- `study_tasks.related_chapter_id` exists in SQLite schema 5 and is nullable.
- SQLite migration 5 adds `related_chapter_id INTEGER REFERENCES subject_chapters(id) ON DELETE SET NULL`.
- SQLite creates `idx_study_tasks_related_chapter_id`.
- Browser fallback normalizes legacy task objects missing `related_chapter_id` to `null`.
- Browser fallback validates that a chapter task references an existing chapter and that task `subject_id` matches chapter `subject_id`.
- Browser fallback chapter delete and clear-detailed paths set matching task `related_chapter_id` to `null`.
- SQLite and browser fallback task queries use the same task status ordering: `doing`, `todo`, `skipped`, `done`, then unknown.
- SQLite and browser fallback task queries use the same tie-breaker shape: `created_at ASC`, then `id ASC`.

| Area | SQLite | Browser fallback | Impact | Recommendation |
| --- | --- | --- | --- | --- |
| Subject list ordering | `subjectsRepository.getAllSubjects` uses `ORDER BY name` | `subjectsApi.getAll` sorts by `order` and mutates `subjectsRef.current` | Progress and settings subject list order can differ across Electron/browser fallback | Do not change in this audit. Potential issue:

| Area | SQLite | Browser fallback | Impact | Recommendation |
| --- | --- | --- | --- | --- |
| Pomodoro equal-total stats | SQLite range stats order by `total_minutes DESC`; no tie-breaker | fallback `pomodoroApi` and `pomodoroStats` sort by `total_minutes DESC`; no tie-breaker | Subject stat order may differ when totals tie | Add `subject_id/name` tie-breaker in a focused low-risk PR if UI stability matters. |
| Mistake equal-created ordering | SQLite `ORDER BY m.created_at DESC`; no id tie-breaker | fallback sorts by `created_at DESC`; no id tie-breaker | Equal timestamp rows can flip | Add `id DESC` or equivalent in both paths if review list jitter is observed. |
| Entry equal-date ordering | SQLite and fallback primarily order by date only | Multiple entries for one date should not normally exist through normal UI, but imports may create edge cases | Low | Keep documented; test only if import allows duplicates. |

## Migration Parity

Verified fact:

- SQLite has formal migration semantics through `PRAGMA user_version`.
- Browser fallback has no formal schema version. It normalizes known missing task field `related_chapter_id` during `DataProvider` initialization.

Risk:

- Future fallback fields can silently remain absent unless each new persisted field gets an explicit normalization path in `DataContext.tsx`.

Recommendation:

- For every future schema-affecting field, require a fallback migration note and at least one localStorage legacy fixture test.

## New Test Coverage Added

Verified fact:

- `tests/studyTaskParity.test.ts` adds fixture-based parity tests:
  - same planned-date fixture returns identical full task rows and deterministic order after timestamps are controlled;
  - chapter delete nulls `related_chapter_id` without deleting the task in both paths;
  - cross-subject chapter attribution is rejected in both paths.
- `tests/databaseMigrations.test.ts` now strengthens schema 4 to 5 migration assertions:
  - migration can run idempotently;
  - old task fields are preserved;
  - `related_chapter_id` is null for old rows;
  - `idx_study_tasks_related_chapter_id` exists;
  - FK points to `subject_chapters(id)` with `ON DELETE SET NULL`;
  - `PRAGMA foreign_key_check` is clean.

Validation:

- `npx.cmd vitest run tests/databaseMigrations.test.ts tests/studyTaskParity.test.ts` passed with 2 files and 17 tests.

## Conclusion

Evidence supports the v1.13.0 claim that chapter task query ordering and chapter deletion semantics are aligned between Electron SQLite and the real browser fallback data layer.

Evidence does not support broad parity claims for every adjacent module. Subject list ordering and some non-task aggregate tie-breakers still need follow-up decisions, but they are not blockers for v1.13.1 unless the next release scope explicitly targets display-order parity.
